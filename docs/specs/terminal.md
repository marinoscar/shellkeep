# Terminal: sessions, gateway and browser

> **Audience:** developers · Code: `apps/api/src/terminal/`, `apps/api/src/ssh/`, `apps/web/src/services/terminal-ws.ts`, `apps/web/src/components/terminal/` · Related: [ARCHITECTURE.md](../ARCHITECTURE.md#3-domain), [SECURITY-ARCHITECTURE.md](../SECURITY-ARCHITECTURE.md#3-terminal-websocket-authorization), [terminal-ai.md](terminal-ai.md)

## 1. Purpose

Give a signed-in user a terminal in the browser on any server they may connect to, that **survives** closing the tab, the laptop or the API process: the shell runs inside tmux on the target server, and the browser is only a view of it. This spec defines the session model, the WebSocket protocol between browser (or CLI) and API, the reaper, the browser-side layout rules that keep scrolling and mobile input working, and the invariants that must not break.

## 2. Model

### 2.1 Session

A **terminal session** (`terminal_sessions`) is one user's handle on one tmux session on one server profile. Columns: `user_id`, `org_id`, `server_profile_id`, `name`, `status`, `tmux_session_id` (`sk-` plus the first 8 hex characters of a UUID, generated by the API and matched by `^[A-Za-z0-9_.-]+$` before it is ever placed in a command), `cols`, `rows`, `last_activity_at`, `terminated_at`. A session is **personal**: each person who connects to a shared server opens their own, and the sharing slice has no `terminal_session` resource type.

Creating a session (`POST /api/sessions`) requires `sessions:write` and the `connect` action on the server profile (owner, group member or grantee as `operator` or better); anything else is 404. It reads no credential and opens no connection: the SSH connection starts at the first `connect` message.

### 2.2 Status machine

| From | To | Cause |
|---|---|---|
| (new) | `active` | row created |
| `active` | `detached` | the last WebSocket attached to it closed; or the reaper: idle for `terminal.detachAfterMinutes` |
| `detached` | `active` | a client sends `connect` and the SSH connection starts or re-attaches |
| `detached` | `terminated` | the reaper: idle for `terminal.terminateDetachedAfterHours` |
| `active`, `detached` | `terminated` | `DELETE /api/sessions/:id`, `POST /api/sessions/batch-terminate`, or the SSH stream closing (the shell exited) |
| `terminated` | (row deleted) | the reaper: older than `terminal.purgeTerminatedAfterDays` |

`terminated` is final: `connect` answers `session_error` `TERMINATED`. Defaults 60 minutes, 12 hours and 3 days; bounds 5 to 1440 minutes, 1 to 720 hours, 1 to 365 days. Activity (`last_activity_at`) is bumped, throttled, by terminal input.

### 2.3 What a connection is

One authenticated socket attaches to at most one session. The API keeps **one SSH connection per running session** (`SessionManagerService`), shared by every socket attached to that session (a second tab or the CLI sees the same stream); the SSH connection closes when its stream ends, not when the last socket leaves. After an API restart no SSH connection exists: the next `connect` opens one and re-attaches to the surviving tmux session.

### 2.4 tmux

`SshService.connect` opens an interactive shell with a PTY (`xterm-256color`) through `SshConnectionFactory` (host key verified first, purpose `interactive`) and writes:

```
tmux new-session -As <tmuxSessionId> \; set-option history-limit 50000 \; set-option mouse on
```

`-A` attaches if the session exists, else creates it. `history-limit 50000` and `mouse on` are applied at attach; tmux mouse mode is what makes the wheel scroll the pane's history (§5.2). An existing tmux session keeps the options it was created with.

### 2.5 History

`GET /api/sessions/:id/history` downloads the pane's scrollback as `text/plain` (`sessions:read`, owner only, 400 for a terminated session). `SessionHistoryService` is the **only** reader of a pane: it runs `tmux capture-pane -p [-J] -S -<lines> -t <id>` and `display-message ... '#{pane_current_path}'` over an exec channel. The download keeps raw wrapping (`joinWrapped: false`); AI features use joined lines and go through the consent and redaction gate ([terminal-ai.md](terminal-ai.md)). The guard spec `test/terminal-ai/capture-boundary.spec.ts` fails if `capture-pane` appears anywhere else.

## 3. WebSocket protocol

Endpoint `WS /api/terminal/ws` (`@WebSocketGateway({ path })`, `ws` adapter). Text frames are JSON control messages; binary frames are terminal bytes. A text frame that does not parse is ignored (logged); an unknown `type` is ignored. The heuristic for a binary frame that arrives as a Buffer: it is control JSON only when its first byte is `{`.

### 3.1 Client to server

| Message | Fields | Effect |
|---|---|---|
| `auth` | `token` (access JWT or `pat_` token) | Authenticates; when already authenticated, replaces the token (refresh) |
| `connect` | `sessionId` (UUID) | Starts or re-attaches the session; needs a live socket and no maintenance window |
| `resize` | `cols`, `rows` | Resizes the PTY of the attached session |
| `ping` | none | Answered with `pong` |
| binary | raw bytes | Terminal input, written to the SSH stream of the attached session |

### 3.2 Server to client

| Message | When |
|---|---|
| `auth_ok` | first authentication succeeded |
| `auth_refreshed` | a re-`auth` on an authenticated socket succeeded (no `connect` follows) |
| `auth_fail` `{ reason }` | authentication or a `connect` was refused; the socket is closed except when a `connect` is refused for maintenance |
| `auth_expired` | the access token's `exp` passed with no fresh `auth`; the socket then closes |
| `session_ready` `{ sessionId }` | attached; terminal output follows as binary frames |
| `session_error` `{ error, code }` | a `connect` failed, codes in 3.4 |
| `session_ended` `{ reason }` | `terminated` (an explicit terminate), `stream_closed` (the shell exited) or `access_revoked` (a sharing change, grant revoked or downgraded, member removed or group deleted, means this client may no longer connect to the server: it is detached, its socket stays open, and the SSH stream and tmux keep running for any other permitted client) |
| `pong` | answer to `ping` |
| binary | terminal output |

The server also sends a protocol-level WebSocket ping every 30 seconds. The browser sends a JSON `ping` every 15 seconds (`TerminalWebSocket.PING_INTERVAL_MS`) and shows the round trip as latency.

### 3.3 `auth_fail` reasons

The wire `reason` is a string; the metric label (`app.terminal.ws.auth_denied`) is a bounded value. Both lists are asserted against the code by `apps/api/test/docs-consistency.spec.ts`.

<!-- ws-reasons:start -->
| Metric reason | Wire `reason` | Meaning |
|---|---|---|
| `timeout` | `Authentication timeout` | no `auth` within 5 seconds |
| `invalid_token` | `Invalid token` | malformed, forged or unverifiable token, or a resolver error |
| `expired` | `Invalid token` on `auth`; an `auth_expired` frame on a live socket | token past `exp` |
| `forbidden` | `forbidden`, or `Invalid user` | principal lacks `sessions:write`; a re-auth as another user or organization (`forbidden`); an inactive user or one without an organization (`Invalid user`) |
| `maintenance` | `maintenance` | a maintenance window refuses a new authentication or a new `connect` |
<!-- ws-reasons:end --><!-- ws-reasons:end -->

`Not authenticated` is sent when `connect` arrives before a successful `auth`. The browser maps `forbidden`, `maintenance` and `auth_expired` to non-reconnecting states (`forbidden`, `maintenance`, `expired` events); everything else shows the reason.

### 3.4 `session_error` codes

| Code | Meaning |
|---|---|
| `NOT_FOUND` | not a UUID, not the caller's session, the server is no longer connectable by the caller (a revoked share), or the profile is gone: indistinguishable on purpose |
| `TERMINATED` | the session is terminated |
| `ATTACH_FAILED` | the SSH connection exists but the socket could not be attached |
| `CONNECTION_FAILED` | any other failure opening SSH (message is the error text) |
| `HOST_KEY_UNKNOWN`, `HOST_KEY_MISMATCH` | the host key check refused before any credential was sent; the frame also carries `presented`, `expected` (null when none pinned) and `serverProfileId`. The socket stays open; after the user trusts the key the client sends `connect` again |

### 3.5 Connection sequence

```
client                                  gateway
  │ ── auth {token} ───────────────────> │ resolve principal, sessions:write, maintenance
  │ <────────────────────── auth_ok ──── │ ping timer, expiry timer armed
  │ ── connect {sessionId} ────────────> │ owner check, assertCanConnect, getDecryptedProfile('connect')
  │                                      │ ssh open (host key first) -> tmux new-session -As ...
  │ <───────────────── session_ready ─── │ status -> active
  │ <═══════ binary output ══════════════│
  │ ═══════ binary input ═══════════════>│
  │ ── auth {fresh token} (every refresh) > │ ── auth_refreshed
```

The browser refreshes the token `min(60 s, 20% of its lifetime)` before `exp` and never twice within 10 seconds; on `auth_expired` it tries one refresh and reconnect before giving up. The CLI (`shellkeep sessions attach`) re-sends `auth` every 10 minutes; a PAT socket expires after 15 minutes without a re-auth.

### 3.6 Limits

Auth deadline 5 s; WebSocket ping 30 s; nginx read and send timeouts 3600 s on this location (an idle terminal is normal; one hour bounds a forgotten tab); proxy buffering off. A re-auth never touches a running stream, and a maintenance window never cuts an open socket.

## 4. Extending it

- **A new control message.** Add a `case` in `handleControlMessage`; check `isLive(client, state)` first; validate every field (never trust a client id); add the matching branch in `terminal-ws.ts`; document it in 3.1 and 3.2; extend `terminal.gateway.spec.ts` and `test/terminal/terminal-gateway.authz.spec.ts`.
- **A new `session_error` code.** Send it from `handleConnect`, add it to 3.4 and to the browser's `readHostKeyRefusal`/error mapping; a code that discloses existence (as opposed to `NOT_FOUND`) needs a security review.
- **A new way to open SSH.** Always `SshConnectionFactory.open(profile, { purpose })`; never `ssh2` directly (`test/ssh/ssh-boundary.spec.ts`). Credentials come from `ServerProfilesService.getDecryptedProfile(id, principal, purpose)`.
- **A new reader of the pane.** Add a method to `SessionHistoryService`; route anything bound for a model through `TerminalContextService.forAi`.
- **A new reaper step.** Add a bounded, idempotent statement to `SessionReapHandler.reap()` (the queue delivers at least once), count it in `app.terminal.sessions.reaped` with a new `action`, and notify after the commit.
- **A new user terminal setting.** Add it to `terminal.user-settings.ts` (Zod, optional, with a default) and `apps/web/src/lib/terminal/settings.ts`; the settings page is `apps/web/src/components/terminal/settings/`.
- **A new webhook event or alert rule.** `terminal/webhooks/terminal.webhook-events.ts` (permanent keys, strict payload schema, ids and names only) and `terminal/alerts/terminal.starter-alert-rules.ts`.

## 5. The browser terminal

### 5.1 Stack

xterm.js in `TerminalView`, driven by `useTerminal` and `TerminalWebSocket`. The workspace page `/sessions/:id` holds tabs and split panes (`WorkspaceTabs`, `SplitLayout`); every open tab keeps its pane mounted (xterm and socket) and off-screen panes are hidden by `visibility: hidden` and a far negative `left`, never `display: none`. Below `sm` only the active pane is on screen. A key bar (`TerminalKeyShortcutsBar`, user shortcuts in the `shortcuts` namespace), scroll buttons, a status bar (connection, latency, server chip) and the AI panel (`md` and up) are siblings of the panes.

### 5.2 Scrollback chain

| Layer | Where | Capacity |
|---|---|---|
| Server history | tmux `history-limit` | 50,000 lines |
| Transport | WebSocket binary stream | in flight only |
| Client buffer | xterm `scrollback` (user setting `terminal.scrollback`) | 1,000 to 50,000, default 5,000 |
| Viewport | rendered rows | visible |

When tmux attaches, the terminal uses the **alternate screen**, which has no scrollback; xterm then turns wheel events into arrow keys. tmux `mouse on` makes tmux capture the wheel and scroll its own history, which is why it is set at launch and why an existing session needs a re-create to pick it up.

### 5.3 Layout rules (do not break)

1. **One chain from `<main>` to the xterm host.** `ShellLayout` `<main>` is full-bleed (`useShellMainVariant('full-bleed')`); the page root is `flex: 1, minHeight: 0, position: relative`; the frame is absolutely positioned, a flex column whose `bottom` is the key dock offset. Every flex container or item on the chain has `minHeight: 0`, and **none has `overflow: hidden`**. `__tests__/pages/TerminalWorkspace.workspace.test.tsx` walks the chain and fails on a violation.
2. **xterm manages its own scroll in JavaScript.** Never override `.xterm-viewport` CSS, and never hide the terminal with `display: none` (xterm drops scroll events when `offsetParent` is null).
3. **`touch-action: none`** on the terminal container (not on `.xterm-viewport`) so the browser does not claim touch gestures.
4. **The FitAddon host is measured.** Nothing with padding or a gutter may sit inside it; the status bar and key dock are siblings below it. `fit()` is debounced about 100 ms because the virtual keyboard fires a burst of resizes.
5. `.xterm` is `height: 100%`, `padding: 4px`, `box-sizing: border-box`. xterm is initialised with `letterSpacing: 0` and `lineHeight: 1`: WebKit's default metrics otherwise drift the cursor on tablets.

### 5.4 Touch and mobile input

- `useTouchScroll` converts a one-finger vertical swipe (2 px threshold, sensitivity 2.0) into synthetic `WheelEvent`s through `dispatchXtermScroll`, so tmux mouse mode does the scrolling; `TerminalScrollButtons` (setting `showScrollButtons`) sends the same events, tap or hold.
- `useKeyboardInset` derives the covered height from `visualViewport` (`innerHeight - (vv.height + vv.offsetTop)`, ignored under 75 px); the key bar sits at that inset above the keyboard.
- xterm's helper textarea is given `inputmode="text"` so the alphanumeric keyboard opens; an earlier `inputmode=none` hid the keyboard on phones.
- `TerminalKeyShortcutsBar` provides Esc, Tab, Ctrl, arrows and user-defined keystrokes (up to 50), encoded by `encodeKeystroke`.
- **Android TWA.** The app opens at `/sessions` in Chrome's engine; Chrome 108+ resizes only the visual viewport for the keyboard, which `useKeyboardInset` already handles. Not exercised on a physical device in CI; verify by focusing the terminal, checking that the key bar rises above the keyboard, rotating with the keyboard open, and launching from the icon ([runbooks/android-app.md](../runbooks/android-app.md)).

### 5.5 Pitfalls

`overflow: hidden` anywhere on the chain breaks scroll; a missing `minHeight: 0` lets a parent grow unboundedly; a `display: none` tab silently drops scroll; padding inside the FitAddon host shifts the row count; changing a single one of the five breakpoint gates ([AGENTS.md](../../AGENTS.md)) breaks phone layout.

### 5.6 File links in terminal output

Issue #155 (epic #151). A path printed in the output becomes a link that opens a small menu. Code: `apps/web/src/lib/terminal/file-links.ts` (detection), `file-stat-cache.ts` (existence check), `file-link-provider.ts` (the xterm link provider), `apps/web/src/components/terminal/files/` (`useTerminalFileLinks`, `TerminalFileLinkMenu`). The routes it calls are in [files.md](files.md).

**Detected.** Absolute paths, `~/` paths, `./` and `../` paths, and bare relative paths that contain a `/` or end in a known file extension, each optionally followed by `:line`, `:line:col` or `(line,col)`. **Excluded:** URLs and anything inside one, email addresses and `user@host:` remotes, pure numbers, dates and version strings, flags, and a bare name whose extension is not a known file type (`example.com` stays text).

**Tokenizer.** One single-class regex cuts a line into tokens, URL spans are masked first with a literal-scheme regex, and each token is classified with plain string checks, so cost is linear in the line. A token over 1024 characters is ignored, and a line yields at most 8 references.

**Existence check.** Nothing is looked up when output arrives. A `stat` (`GET .../files/stat`, relative to the session's working directory) is sent only when a candidate is hovered or tapped. Answers, found or not, are cached for 30 s per session and path (500 entries at most); a request for a path already in flight shares it; at most 3 stats run at once, the rest wait in order. Any failure (404, refused, network) counts as missing: no link, and no retry until the entry expires. Only a path that exists is underlined.

**Menu.** Click, or a tap on a known link, opens `TerminalFileLinkMenu` at the pointer:

| Action | Behaviour |
|---|---|
| Open | Opens the file viewer (`useOpenFile`), at the printed line when there is one ("Open at line N"). A binary file still opens; the viewer shows its binary card |
| Download | Requests a download token and lets the browser download the file ([files.md](files.md#downloads)) |
| Show in file browser | Present only when the host passes `onShowInFileBrowser` (#156) |
| Copy path | Copies the resolved absolute path |

A directory (a symlink counts as its target) offers only Show in file browser and Copy path.

**Touch.** There is no hover, so a tap checks the path and its underline appears; a second tap on the underlined path, or a long-press (500 ms) on any path, opens the menu. A finger that moves more than 10 px is a scroll and never opens anything. The listeners are passive and never call `preventDefault`, so `useTouchScroll` and the `touch-action: none` rule of section 5.3 are untouched; the click a tap leaves behind is ignored for 800 ms.

**Access.** Links exist only for a holder of `sessions:write`, the rule the files API enforces: `TerminalWorkspacePage` passes the pane a profile id only when the user can write.

**Opt-in.** `TerminalView` takes a `fileLinks` prop (`{ profileId, onShowInFileBrowser? }`) and hands `useTerminal` an `options.fileLinks` source. Without them no link provider does any work and no stat is ever sent.

### 5.7 Touch keys: model and encoder

Issue #165 (epic [#171](https://github.com/marinoscar/shellkeep/issues/171)). The data model and byte encoder behind the on-screen key bar. Code: `apps/web/src/lib/terminal/keys/` (`keyModel.ts`, `encodeKey.ts`, `legacyAdapter.ts`), `apps/api/src/terminal/settings/` (`key-layout.schema.ts`, `shortcuts.user-settings.ts`, `keys/key-model.ts`), `apps/api/prisma/settings-migrations/terminal-shortcuts-v2.ts`.

**Catalog.** `KEY_CATALOG` lists every built-in key by a stable `id`. Ids are stored in the user's `shortcuts.layout`: never rename or remove one. Each entry has a `kind`, a `label`, a default `span` (1 or 2 cells of the 4-column grid) and `repeatable` (holding the key repeats it).

| Kind | Entries (ids) | Notes |
|---|---|---|
| `key` | `esc`, `tab`, `shift+tab` (span 2), `enter`, `backspace` (span 2), arrows `left` `down` `up` `right`, `home`, `end`, `pgup`, `pgdn`, `insert`, `delete`, `f1` to `f12`, `ctrl+c`, `ctrl+d`, `ctrl+z`, `ctrl+\` | Carries a `chord`: what it sends. Repeatable: `backspace`, the arrows, `home`, `end`, `pgup`, `pgdn`, `delete` |
| `modifier` | `ctrl`, `alt`, `shift` | Arms a modifier for the next key; sends nothing itself |
| `action` | `ai`, `arrow-drag`, `attach-file`, `snippets` | Runs an app action; sends nothing |

A layout entry can also be an inline, user-made key: a `macro` (1 to 8 chords sent in order, for example the tmux prefix `ctrl+b` then `o`) or a `custom` key (a label plus a literal sequence). A chord is `{ modifiers, key }` where `key` is a named key (`Escape`, `Tab`, `Enter`, `Backspace`, `Space`, arrows, `Home`, `End`, `PageUp`, `PageDown`, `Insert`, `Delete`, `F1` to `F12`) or one printable ASCII character; modifiers are `ctrl`, `shift`, `alt`, `meta`.

**Mirrored model.** `keyModel.ts` is pure and import-free so the web app and the API share it. `packages/shared` is hand-written CommonJS the web app does not consume, so the file is mirrored: `apps/web/src/lib/terminal/keys/keyModel.ts` is the one to edit, and `apps/api/src/terminal/settings/keys/key-model.ts` is a byte-identical copy. The parity test in `keyModel.test.ts` (web, Vitest) fails if the two differ. Copy the web file over the API one after every edit. The encoder is web-only: the API never produces key bytes.

**Layout shape and caps.** `shortcuts.layout` is `{ groups: [{ keys: [entry] }] }`; an entry is `{ id, span? }` (a catalog key) or `{ key, span? }` (an inline key). A group is one row of the grid. `shortcuts.layout` and `shortcuts.options` are both optional in the namespace and validated by `keyLayoutSchema` and `keyOptionsSchema` (`.strict()`, every field required).

| Cap | Value |
|---|---|
| Groups per layout | 40 |
| Keys per group | 4, spans totalling at most 4 cells |
| Inline (macro and custom) keys per layout | 50 |
| Chords per macro | 8 |
| Label length | 1 to 40 characters |
| Custom sequence | parsed result 1 to 64 characters |

An inline key id must be a UUID and unique in the layout. A catalog id the model does not know is refused. A macro with more than one chord defaults to span 2 (`entrySpan`). A custom sequence accepts the escapes `\xNN`, `\e`, `\r`, `\n`, `\t` and `\\`; a lone trailing backslash, an unknown escape or a malformed `\x` is rejected, at save time by the schema and at encode time by `encodeKey`, which throws.

**Options.** `shortcuts.options` is `{ autoHideWithHardwareKeyboard, haptics }`, both booleans, both true by default (`DEFAULT_KEY_OPTIONS`): hide the key row while a hardware keyboard is in use, and vibrate briefly on each press where supported. A user with no stored layout gets `DEFAULT_KEY_LAYOUT`: the four actions, `shift+tab esc ctrl`, the arrows, four tmux macros (prefix `ctrl+b`, then `o`, `x`, `%`, `"`), `alt tab ins del`, `home pgUp pgDn end`, then F1 to F12 in rows of four.

**Encoder.** `encodeKey(key, { modifiers?, applicationCursor? })` returns the bytes to write to the terminal. `key` is a catalog id, a chord, or an inline key. It follows the sequences xterm.js sends for a hardware key.

- **Cursor keys** (arrows, Home, End). Normal mode sends `ESC [ A` (`B` `C` `D`, `H`, `F`). Application cursor mode (DECCKM, passed as `applicationCursor`) sends `ESC O A`. With any modifier the application form never applies.
- **Modifier parameter.** `m = 1 + shift(1) + alt(2) + ctrl(4) + meta(8)`. When `m > 1`, arrows, Home and End send `ESC [ 1 ; m X`.
- **Tilde keys.** Insert `2~`, Delete `3~`, PageUp `5~`, PageDown `6~`: `ESC [ n ~`, or `ESC [ n ; m ~` when modified.
- **F-keys.** F1 to F4 send `ESC O P/Q/R/S`, or `ESC [ 1 ; m P/Q/R/S` when modified. F5 to F12 send `ESC [ n ~` with n = 15, 17, 18, 19, 20, 21, 23, 24, or `ESC [ n ; m ~` when modified.
- **Control characters.** Ctrl with a letter sends the control character (`ctrl+c` is `\x03`). Ctrl with `@`, space, `[`, `\`, `]`, `^`, `_`, `?` and `3` to `8` sends NUL, ESC, FS, GS, RS, US and DEL as xterm does; any other Ctrl character is sent unchanged. Ctrl+Backspace sends `\b`, plain Backspace `\x7f`, Ctrl+Space NUL. Shift with a lowercase letter sends the uppercase letter. Shift+Tab sends `ESC [ Z`.
- **Alt.** Alt prefixes the base bytes with ESC (`alt+x` is `ESC x`), also on Tab, Enter, Backspace, Escape and Space. On cursor, tilde and F-keys Alt is part of the modifier parameter instead.
- **Armed modifiers.** The `modifiers` option (the Ctrl, Alt and Shift keys of the bar) is added to the chord's own. A `modifier` or `action` catalog key encodes to the empty string.
- **Macro.** Each chord is encoded by its own modifiers, concatenated in order. Armed modifiers do not apply; `applicationCursor` does.
- **Custom.** The parsed sequence, verbatim.

Deliberate differences from xterm.js: Alt+arrow is `ESC [ 1 ; 3 X` (xterm rewrites it to Ctrl+arrow on Linux), and Shift+PageUp, Shift+PageDown and a modified Insert are sent (xterm scrolls its own buffer or sends nothing). An unknown id or key name throws.

**Settings migration (v1 to v2).** The v1 `shortcuts.keyShortcuts` list stays; `layout` is added beside it. Epic #171 decided every user gets the default first page, so `terminal-shortcuts-v2.ts` writes, for every stored row that has a v1 list and no `layout`, `DEFAULT_KEY_LAYOUT` (the actions, the Ctrl and Alt toggles, the arrows, the tmux macros, the navigation keys and F1 to F12) followed by the user's v1 shortcuts that the default does not already send. A shortcut is dropped when it sends the same bytes as a default key (its chord sequence, modifiers order ignored, equals a default key's) or is an unchanged v1 default (stable id and chords), so a user who kept the v1 defaults gets exactly `DEFAULT_KEY_LAYOUT`. The rest are appended as inline macros (id, label and chords kept) in rows of at most four cells (a multi-keystroke macro takes two), within the caps: what would exceed 40 groups or 50 inline keys is dropped. A malformed shortcut is skipped. The row's `options` gets `layoutVersion: 2` (an optional field of `keyOptionsSchema`; absent `autoHideWithHardwareKeyboard` and `haptics` are filled with `true`), and the namespace merge keeps it when a client saves options without it. A row the first version of this step wrote (a layout of inline macros only, no catalog key, no `layoutVersion`) is upgraded the same way, from its `keyShortcuts` or, with none, from its macros; the marker makes both cases run once, so the step is idempotent and cannot loop. A row with a layout the user saved (it has catalog keys) or with `layoutVersion` is left alone. The seed runs it (`prisma/seed-app.ts`, `migrateKeyLayout`). A written row's `version` is incremented, so clients refetch instead of saving over it (`If-Match`). `keyShortcuts` is not removed: it is the rollback source and feeds the legacy editor, whose save rewrites the layout through `layoutFromLegacyShortcuts` (the same default plus extras; the web also uses it for a v1 row not migrated yet). The step is Nest-free because the seed image has no `src/`, so it carries copies of `DEFAULT_KEY_LAYOUT` and of the packing of `legacyShortcutsToDefaultLayout`, and tests keep them equal. Logs carry counts only, never sequences.

Rollback, before reverting #165, from `apps/api` with `DATABASE_URL` set: `npx ts-node --transpile-only -P prisma/tsconfig.json prisma/settings-migrations/terminal-shortcuts-v2.ts --revert`. It drops `layout` and `options` from every row that has either.

**Legacy adapter.** Since #167 the key row and panel render the v2 layout directly (section 5.9). `toLegacyBarKeys` in `legacyAdapter.ts` is kept for the legacy shortcuts editor until #169 replaces it: a catalog `key` becomes its chord (id `catalog:<id>`), a macro keeps its id, label and chords, and modifier, action and custom keys, which have no v1 form, are left out. `fromLegacyShortcuts` is the inverse for a v1 list.

### 5.8 Touch keys: modifiers and pop-ups

Issue #166 (epic [#171](https://github.com/marinoscar/shellkeep/issues/171)). Code: `apps/web/src/lib/terminal/keys/` (`modifierState.ts`, `modifiedInput.ts`, `popupKeys.ts`, `haptics.ts`), `apps/web/src/hooks/useModifierState.ts`, `apps/web/src/components/terminal/useLongPress.ts`, `TerminalKeyShortcutsBar.tsx`, `useTerminal.ts`.

**State machine.** Ctrl, Alt, Shift and Meta are each `off`, `armed` or `locked`. A tap arms; a second tap within 300 ms of the arming tap locks; a later second tap turns it off; a tap on a locked modifier turns it off. Modifiers combine. `consume()` is called once for every key sent, from any source, and returns the active modifiers while turning the armed ones off; locked ones stay. The state is a small external store (`createModifierStore`), not React state, because the terminal's `onData` handler reads and consumes it synchronously; `useModifierState` subscribes components. The workspace owns one store for all panes.

**Bar keys.** The bar draws the layout's `ctrl`, `alt` and `shift` catalog keys as toggles (`toBarModifierKeys`, in layout order; a layout converted from a v1 list has none). Off is outlined, armed is filled-tonal, locked is filled with a lock dot; the toggle has `aria-pressed` and an accessible description `armed` or `locked`. A bar key is encoded by `encodeBarShortcut` with the consumed modifiers and the pane's cursor-key mode (`terminal.modes.applicationCursorKeysMode`): Ctrl then → sends `ESC [ 1 ; 5 C`, a bare → in application mode `ESC O C`. Without modifiers in normal mode the bytes are exactly the v1 `encodeShortcut` ones. A multi-keystroke shortcut (a macro) ignores the armed modifiers but still releases them.

**Typed input.** `useTerminal` passes every `onData` chunk through the `inputModifiers` interceptor (`createModifierInputInterceptor`), given by the workspace through `WorkspacePane` and `TerminalView`. The hook point is `onData`, after xterm has turned a keystroke or a soft-keyboard input event into text, so the phone keyboard, IME and hardware keys all pass through one place. When a modifier is active and the chunk is exactly one key, it is re-encoded with `encodeChord` and the one-shots are released: one character (one code point; `\r`, `\t`, `\x7f`, `ESC` and space are Enter, Tab, Backspace, Escape and Space) or one of xterm's own key sequences (arrows, Home, End, PgUp, PgDn, Insert, Delete, F1 to F12, in either cursor mode). Ctrl+`r` sends `\x12`, Alt+`b` sends `ESC b`.

**Pastes and IME (decision).** Input of several characters at once (a paste, bracketed or not, or an IME commit of a whole word) is sent unchanged and the modifiers stay as they are: applying Ctrl to a paste, or to only its first character, is never what the user meant. Any other escape sequence (focus reports, mouse reports) is also passed through without consuming, since the terminal sends those on its own. A single pasted character counts as one key.

**Hardware keyboards win.** A keydown carrying a real `ctrlKey`, `altKey` or `metaKey` (seen in xterm's custom key handler) releases the armed one-shots, and the data xterm produces for that keydown (synchronously, within the same task) is sent unmodified, so nothing is applied twice. A locked modifier stays locked and applies again to the next soft key. A hardware key without modifiers is treated like a soft key.

**Pop-ups.** A press of 450 ms that does not move more than 10 px, or the context menu (right-click, the Menu key, Shift+F10, a platform long press), opens a menu above the key: Ctrl gives Ctrl+C, D, Z, R, L, A, E, W, U, K; Alt gives Alt+B, Alt+F, Alt+.; an arrow gives Home, End, PgUp, PgDn. A long press never also taps the key. The menu is an MUI `Menu` (keyboard navigable, closed by Escape or an outside tap); choosing an entry sends its chord with the consumed modifiers and closes it.

**Haptics.** With `shortcuts.options.haptics` on and `navigator.vibrate` present (Android), a modifier toggle vibrates for 10 ms.

### 5.9 Key row and panel

Issue #167 (epic [#171](https://github.com/marinoscar/shellkeep/issues/171)). Code: `apps/web/src/lib/terminal/keys/keyRow.ts` (`resolveKeyGroups`, `encodeResolvedKey`, `popupOf`), `apps/web/src/components/terminal/TerminalKeyShortcutsBar.tsx` (the row), `components/terminal/keys/` (`TouchKey`, `TerminalKeyPanel`, `useAttachFile`), `pages/TerminalWorkspacePage.tsx`.

**Source.** Both read the user's v2 `keyLayout` from `useTerminalSettings`, resolved by `resolveKeyGroups`: each entry gets its kind, label and span; an action the host cannot run is left out and a group left empty is dropped. Nothing renders from `keyShortcuts` any more; the legacy editor still writes both lists.

**Accessory row.** One continuous horizontal scroller (no pages): the groups in order, flattened, with a thin divider between groups; a span-2 key is two 44 px targets wide. The panel toggle (accessible name "Key panel", `aria-expanded`, `aria-controls`) is pinned at the right end outside the scroller, so it never scrolls away. The row's height is fixed and it stays the key dock's first child, on the keyboard (section 5.4).

| Kind | Drawn as |
|---|---|
| `modifier` | The section 5.8 toggle (off, armed, locked), with its pop-up |
| `key` | A plain key by label; arrows have the navigation pop-up. Repeatable keys carry `data-repeatable` for hold-to-repeat (#168) |
| `macro`, `custom` | A plain key by label |
| `action` | Icon and label. `ai` ("Open AI assistant") only with the AI feature and `ai:use`; `attach-file` only with `sessions:write` and a server; `arrow-drag` and `snippets` are hidden until #168 and #172 |

**Sending.** Every key, from the row or the panel, is encoded by `encodeResolvedKey` with the consumed modifiers and the pane's cursor-key mode (section 5.7, 5.8). After a key the terminal is refocused, except while the panel replaces the keyboard.

**Full key panel.** A region named "Key panel": a tab strip (only "Keys" today; `KEY_PANEL_TABS` is where snippets #172 and history #173 append), a Customize link to `/settings/shortcuts` (the editor, #169), a close button, and a 4-column grid holding every group, one group per grid row, each key spanning 1 or 2 cells. Escape inside the panel closes it (a pop-up's Escape closes only the pop-up). The placement comes from `useTerminalLayout` (no new breakpoint read):

| Layout | Placement |
|---|---|
| Not a phone (`!isPhone`, `sm` and up: tablets, landscape, an unfolded foldable, desktop) | A side panel beside the panes, `min(320px, 40%)` wide so a ~600 px screen keeps most of its width for the terminal. The phone keyboard stays up: the terminal is not blurred and keeps its focus, and Escape gives it back |
| Phone (`isPhone`, below `sm`) | In the key dock under the row, replacing the keyboard at its last height above the page (280 px when none was seen). Opening blurs the xterm textarea to dismiss the OS keyboard and focuses the Keys tab; a keyboard button closes the panel and refocuses the terminal; the keyboard coming back (a tap on the terminal) closes the panel; Escape returns focus to the toggle |

The key panel's rule is deliberately not the AI and Files panels' (`isWide`, `md`): an unfolded foldable in portrait is under 900 px, and the side panel with the keyboard still up is what epic #171 asks for there. The key panel takes turns with the Files and AI panels: opening one closes the others.

**Attach.** The `attach-file` key opens a file picker and uploads the file into the session's working directory: `stat .` with the session resolves the folder, then `uploadRemoteFile` sends it ([files.md](files.md)). It never replaces an existing file: a `FILE_EXISTS` answer tells the user to use the Files panel, which asks.

## 6. Operations

- **Reaper.** `@Cron('0 */5 * * * *')` in `terminal/tasks/session-cleanup.task.ts` enqueues `terminal.session.reap` (enqueue-only). The handler runs three bounded statements in order (detach, terminate, purge), reading the thresholds at run time, then sends one `terminal.session_reaped` notification per owner and one `terminal.session.terminated` webhook (reason `reaped`) per session it terminated, after the commit. It closes the live stream of each session it terminated (best effort, logged on failure; invariant 8) and does not kill remote tmux sessions. Counts go to `app.terminal.sessions.reaped` (`action`: `detached`, `terminated`, `purged`) and the log, never ids or names.
- **Metrics.** `app.terminal.sessions` (gauge by status), `app.terminal.ws.connections`, `app.terminal.ws.auth_denied` (`reason`), `app.terminal.ssh.connect.duration` (histogram, `outcome`), `app.terminal.ssh.connections`, `app.terminal.sessions.reaped`.
- **Alerts** (seeded disabled, keys permanent): `shellkeep.ssh_connect_failures`, `shellkeep.ssh_connect_slow` (kind `terminal_ssh_connect_p95`), `shellkeep.ws_auth_denied_spike`, `shellkeep.reaper_stalled` (kind `terminal_job_stalled`).
- **Webhooks** (audience `user`, ids and names only): `terminal.session.created`, `terminal.session.terminated` (`reason`: `user`, `batch`, `reaped`), `server_profile.host_key_changed`.
- **Doctor checks:** `terminal.tmux.probe` (probes `terminal.doctorProbeProfileId`), `terminal.ssh.client`, `terminal.ssh` egress contributor, `terminal.sessions.reaper`, `terminal.ssh.legacy-secrets`, `ssh.host_key_policy`.
- **Telemetry spans:** `terminal.ws.session` (the socket's attachment, with `session.id` and `org.id` on the span only).
- **Export and purge:** sessions are exported without scrollback and deleted with the user (`TerminalSession`: delete, include).

## 7. Invariants

1. A socket is authorized on every message: the token is validated on `auth`, `sessions:write` is held, expiry is enforced by a timer and re-checked per message, and `connect` re-checks ownership and the right to connect to the server **now**.
2. A client-supplied session id is never trusted: non-UUID, not owned, or not connectable are the same `NOT_FOUND`.
3. The `auth` token never appears in a URL or a log; the logs carry user id and a reason.
4. Maintenance refuses new authentications and attaches only; it never ends a running socket or a token refresh.
5. No SSH connection skips host-key verification; a changed key is never accepted.
6. Terminal bytes are relayed, never stored or logged. The only reader of a pane is `SessionHistoryService`.
7. The `auth_fail`/`session_error` vocabulary above is the contract of the web and CLI clients; a change is a coordinated change of both.
8. **Closing and its limits (verified in code, [#142](https://github.com/marinoscar/shellkeep/issues/142)).** `DELETE /api/sessions/:id`, `POST /api/sessions/batch-terminate` and the reaper's terminate step close the live stream after the row update commits: `SessionManagerService.terminateSession` sends attached clients `session_ended` (reason `terminated`) and closes the SSH stream, through `SessionsService` and, for the reaper, the `LIVE_SESSION_CLOSER` port. A failed close is logged and never fails the request or the job; the row stays terminated. Two cases that once escaped are closed. After a factory reset, user-data purge or organization offboarding job succeeds, `LiveSessionResetListener` (on `JOB_SETTLED_EVENT`) has `LiveSessionReconciler` close every live stream whose session row is missing or `terminated`. When a share changes (`sharing.grant.revoked`, `sharing.grant.updated`, `sharing.group.member_removed`, `sharing.group.deleted`), `TerminalGateway` re-checks each affected attached client with the rule `connect` uses and detaches one that may no longer connect: it sends `session_ended` (reason `access_revoked`) and removes it from the managed session, which, left with no client, is handled as on a normal detach (row `detached`, tmux keeps running). Both run after the triggering write commits, never fail it, and log failures. The one limit that remains: the **remote tmux session is not killed** (deliberate: it is per-host, long-running work, see `app-registrations/user-data.ts`).
