# Platform migration (ShellKeep)

**Applies from #45** (database baseline). Until then the schema is the single hand-written `apps/api/prisma/schema.prisma` with ordinary migrations, and the only rule is: never rewrite a migration that was applied anywhere. After #45 the schema is composed: `apps/api/prisma/schema/` is generated by `platform db compose` from the platform fragments plus `apps/api/prisma/fragments/*.prisma`. There is no `schema.prisma`. Run these from `apps/api`. Background: `docs/DEVELOPMENT.md`; the platform-adoption ledger `docs/platform-adoption/local-exceptions.md` *(target, #40/#83)*; the baseline runbook (#45).

Database work goes to the `database-dev` agent. The main agent does the git steps.

## What you may and may not touch

| Path | Rule |
|---|---|
| `apps/api/prisma/fragments/*.prisma` | Yours: ShellKeep's tables (server profiles, terminal sessions, runbooks) and `extend model` back-relation blocks |
| `apps/api/prisma/schema/` | Generated and committed. Never hand-edit |
| `apps/api/prisma/migrations/` app directories | Yours, created by `prisma:migrate:dev` |
| `apps/api/prisma/migrations/` installed platform directories | Byte copies. Never edit or rename, comments included; the lock hashes the raw bytes |
| `apps/api/prisma/platform.lock` | Written by `db:sync` and `db:baseline`. Hand-edit only `rawSqlIndexes` and `deviations` |
| `apps/api/prisma/drift-allowlist.json` | Yours. See the allowlist rule |

ShellKeep never authors platform migrations. A change to a platform table is a seam request (`gh issue create --template seam_request.yml`). Until it ships, the workaround is a side table keyed by the platform id, or a declared deviation listed in `local-exceptions.md`.

## A. Change an app-owned table

1. Edit the fragment in `apps/api/prisma/fragments/`.
2. `npm run db:compose`.
3. `npm run prisma:migrate:dev -- --name <snake_case_name>`.
4. `npm run prisma:generate`.
5. Run the checks below. Commit the fragment, `prisma/schema/` and the new migration together.

Rules:

- A relation to a platform model needs a back-relation: `extend model User { ... }` in the fragment that owns the foreign key. An `extend` block holds back-relation fields only; a scalar field, an owning relation or a block attribute is refused. `NOT_EXTENSIBLE` means use a side table.
- **SSH credential columns hold ciphertext only**; never add a column that could carry a decrypted secret.
- An org-owned table (from #45) carries `org_id`, forces RLS, and links to other org tables by a composite foreign key including `org_id`. A migration touching an org table runs as `BEGIN; SELECT set_config('app.rls_bypass','on',true); ...; COMMIT;`.
- At most one open PR may carry a migration. A second rebases and regenerates, so its timestamp is newer.
- A new job type needs no migration: `jobs.type` is a plain string.

## B. Take a new platform release

1. Bump `@marinoscar/platform-db` to the exact version in `apps/api/package.json`, then `npm install`.
2. `npm run db:sync`: installs the missing platform migrations as byte copies after ShellKeep's own.
3. Read each new directory under `apps/api/prisma/migrations/`: check for `ALTER` on a table ShellKeep extends and for role or permission data changes.
4. `npm run db:compose`, then `npm run prisma:generate` and fix compile errors. Mark each workaround as a shim (section E).
5. `npm run prisma:migrate`, then the checks below.
6. Commit the new directories and `platform.lock` together. A rename or an edit of an installed directory makes `db:check` fail with `LOCAL_MODIFIED`.

## C. The raw-SQL list rule

Prisma cannot express partial indexes, expression indexes, trigram indexes, generated columns or CHECK constraints. They live only in `migration.sql`. That is intentional drift.

- Never add `@@unique` or `@@index` for one, and never replace one with a `findFirst` before the insert.
- Every partial or expression index goes under `rawSqlIndexes` in `platform.lock` as `{ name, definition }`. Copy `definition` exactly from a migrated dev database: `SELECT indexdef FROM pg_indexes WHERE indexname = '<name>';`.
- The drift test asserts the list against `pg_indexes`. A missing or reworded entry fails with `INDEX_MISSING` or `INDEX_DEFINITION_DIFFERS`.

## D. The drift-allowlist rule

`npm run db:drift` removes the statements in `apps/api/prisma/drift-allowlist.json` and fails on anything left.

- Each entry is `{ statement, reason, removeIn }`; `removeIn` is an issue number.
- An entry is for a statement Prisma prints because its schema language cannot declare the object, or for a declared deviation column. Never add one to hide a real difference on a platform table.
- The PR that closes an entry's `removeIn` issue deletes the entry.

## E. Shims and deviations

- A temporary workaround in code carries `// PLATFORM-ADOPTION-SHIM(<issue that removes it>)` and a row in `docs/platform-adoption/local-exceptions.md`.
- A column ShellKeep adds to a platform table is a deviation in `platform.lock`, a drift-allowlist entry and a ledger row. Avoid it; use a side table.
- The baseline of an existing database is a one-off operator action (rehearse on a restored backup, then `platform db baseline`). Never run it from a deploy update.
- The API connects as an ordinary non-superuser role from #52; do not change `POSTGRES_USER` meanwhile.

## Check before you commit

```bash
cd apps/api
npm run db:compose:check   # prisma/schema/ equals a fresh compose
npm run db:check           # installed SQL equals the package, lock is consistent
npm run db:drift           # replayed migrations equal the schema (needs a shadow database)
npm run typecheck && npm test
```

Flag the change for the docs agent: table inventory in `docs/ARCHITECTURE.md`, and `local-exceptions.md` if a shim changed.
