## Project overview

ShellKeep is a browser-based terminal workspace: persistent tmux-backed sessions on remote servers, SSH server profiles with encrypted credentials, xterm.js in the browser, and a WebSocket gateway at `/api/terminal/ws`. Planned: terminal AI, fleet runbooks, platform shell UI.
Stack: React + MUI + xterm.js (web), NestJS on Fastify + Prisma + Zod (API), PostgreSQL, Passport (Google OAuth), Nginx same-origin, OpenTelemetry + Pino, Docker Compose. Target: Node 24, Prisma 7, zod 4, React 19, MUI 9 (the platform peers).
Start at [README.md](README.md) and [docs/README.md](docs/README.md) (index with a "Doc map by task").

## MANDATORY: Issue-Driven Development

Every feature and bug fix is tracked by a GitHub issue, filed **before** implementation planning is finalized (features) or the fix starts (bugs), and before any worktree or branch is created. `gh issue create` inside the repo infers the repository.

- **New feature**: `gh issue create --template feature_request.yml` (real problem, solution, component, priority, no placeholders). **Larger initiative**: `--template epic.yml`; children reference the epic.
- **Bug fix**: `--template bug_report.yml` (reproduction, expected vs. actual, component, logs). Reuse an existing issue; never file a duplicate.
- **Platform gap seen from the app**: `--template seam_request.yml` instead of editing platform code (see Packages first).
- Link the work with `Fixes #<n>` / `Relates to #<n>` in commits and the PR ([`.github/pull_request_template.md`](.github/pull_request_template.md)). Feature and bug work only; `chore`/`docs`/`refactor` need no issue.

## MANDATORY: Worktree-Based Feature Development

The main checkout stays on `main`. Every feature or fix is developed in a Git worktree.

- Worktrees live under `worktrees/<short-name>` (git-ignored, flat names); branches are `<type>/<short-name>`. The **main agent** creates them after the issue exists: `git worktree add worktrees/<short-name> -b <type>/<short-name>`.
- All development and commits happen inside the worktree. To finish: commit, then `git worktree remove worktrees/<short-name>`; the branch remains for the PR.
- Never check out a feature branch or work on a feature in the main checkout. One worktree per branch; reuse an existing one.
- **Exception**: in a cloud session, or whenever the environment has already put you on a designated branch, work on that branch instead of creating a worktree.

## MANDATORY: Commits, then always a PR

Create clean, frequent commits, then land the work through a pull request. Assume the branch exists and is checked out; subagents never create branches.

**Every change ships as a PR against `main`; never push to `main`.** Order: commit in slices, `git push -u origin <branch>`, open the PR filling in `.github/pull_request_template.md` and linking its issue, merge once CI is green and nothing is outstanding.

- **Green first, merge second.** Never disable, skip or quarantine a check. A red check this diff did not cause is stated on the PR.
- **A merged PR is finished.** Follow-up work is a fresh branch off the updated `main`.
- **Commit early, commit often**: small, coherent, one intent. No unrelated refactors, repo-wide formatting or dependency upgrades. Revert accidental unrelated edits or split them.
- **A behaviour change carries its tests** in the same commit or the next one.
- **Format** (Conventional Commits): `<type>(<scope>): <short imperative summary>`. Types: `feat`, `fix`, `refactor` (no behaviour change), `test`, `docs`, `chore`.
- **Scopes**: `api` `web` `cli` `db` `infra` `auth` `ai` `jobs` `ui` `core` `docs` `tests` `terminal` `runbooks`.
- **Sequence**: `git status`, `git diff`, stage intentionally, `git commit`, `git status`.
- **Tests not run**: still commit, and say so in the body (`Notes: tests not run (DB env not available).`).

Every improvement to the CLI (`apps/cli`, `install.sh`) bumps the version in `apps/cli/package.json`, the only place it lives (`CLI_VERSION` is recorded in deployment state and sent as the User-Agent of every request).

## MANDATORY: Settings UI Pattern

**Applies from #76.** Every settings surface, admin or per-user, is a **registry-driven hub**, not a tab strip and not an ungoverned route. Today's pages (`apps/web/src/pages/*SettingsPage.tsx`) migrate in #76; new settings work waits for it or follows the pattern.

1. **Every settings page is declared in a section registry**: admin cards in `apps/web/src/config/adminSections.tsx` *(target)* (`ADMIN_SECTIONS`), per-user cards in `apps/web/src/config/userSettingsSections.tsx` *(target)* (`USER_SETTINGS_SECTIONS`). A route without a registry entry is unacceptable. Append new cards; never insert between existing ones.
2. **A settings page is never a new tab on an existing settings page.** Tabs only inside one destination, for genuinely **parallel** content (Users and Allowlist).
3. **The card's `permission` is the exact string the API controller enforces**, never invented. Read it off the controller. Writes are gated inside the page, not by a second card permission.
4. **Reuse `SettingsHub` from `@marinoscar/platform-web/settings/ui`**; never fork it.
5. **The five coupled breakpoint gates move together or not at all**, all in `packages/platform-web/src/` of the platform: `ShellLayout` `showRail` (`up('sm')`), `ShellBottomNav` `down('sm')`, `<main>` `pb: { xs: 10, sm: 3 }`, `SettingsHub` `isCompactWindow`, `ShellAppBar` `isCompactWindow`. The boundary is `sm` (600px), never `md`. The terminal workspace must keep working at phone width under them.

## MANDATORY: Every Long-Running Activity Is a Queue Job

**In force since #49.** The queue and the worker-node fleet are the platform's (`src/platform/jobs/`); the session cleanup cron (`apps/api/src/terminal/tasks/session-cleanup.task.ts`) only enqueues the `terminal.session.reap` job (`terminal/jobs/session-reap.handler.ts`).

1. **No long-running work outside the queue.** Anything that outlives the HTTP request, WebSocket message or cron tick that started it is a registered `JobHandler` with a declared `type`, enqueued through `JobsService` (`@marinoscar/platform-api/jobs`). A detached `void this.doX()`, an `@OnEvent` body that connects, downloads or spawns, and a `@Cron` body that works inline are violations. A `@Cron` only decides whether work is due and enqueues it (`enqueueHousekeepingJob`). Interactive terminal I/O is not a job; runbook runs, summaries and exports are.
   - Exactly three permanent exemptions, all the platform's: the lease reaper (`JobStuckResetTask`), `TempFileJanitorTask` and `NodeSecretSweepTask`. Executable form: conformance suites `cron-enqueue-only` and `on-event-no-io`. A fourth needs a platform change.
2. **Node eligibility is the default posture.** A new job type SHOULD carry `nodeResultSchema` + `persistNodeResult` unless it cannot (writes as it goes, reads several tables mid-computation, needs a privilege a remote machine must never hold). Eligibility is derived; there is no `nodeEligible` flag. SSH-executing jobs stay server-only unless a spec says otherwise.
3. **A node never persists a job-scoped credential.** Per-job secrets are issued through `POST /api/nodes/:id/jobs/:jobId/secret`, held in node memory, bounded by the lease; a handler declares the need with `nodeSecretBroker`. SSH credentials are never brokered (see Invariants).
4. **A job type declares its execution profile or takes the default.** `JobHandler.profile` is exactly `{ maxRuntimeMs, maxAttempts }`. Never add `leaseMs` or `heartbeatMs`.
5. **Jobs carry their organization.** `EnqueueJobInput.orgId` is stored on `jobs.org_id` (`null` for system jobs and housekeeping). A handler touching org tables runs under `JobScope.run(job, fn)`.

## MANDATORY: AI Platform Rules

**Applies from #55.** The AI slice is the platform's (`@marinoscar/platform-api/ai`). The slice is mounted (`apps/api/src/platform/ai/`, features in `apps/api/src/app-registrations/ai.ts`); these bind every AI change.

1. **Never import a provider SDK outside `@marinoscar/platform-ai-providers`** (`packages/platform-ai-providers/src/<provider>/`) or a provider folder the app declares to the `ai-no-sdk-leak` suite. A feature imports `AiModule`, injects `AiService` and calls `AiService.forUser(userId, { orgId, feature })`, never an SDK client.
2. **Never call AI from the browser; keys never leave the server.** No route, log line, span, error or usage row carries key material. Only a realtime session's ephemeral secret may be returned.
3. **AI jobs are server-only, permanently.** Every `ai.*` job type implements neither `nodeResultSchema` nor `persistNodeResult`.
4. **Route guards.** Consumer routes under `/api/ai/*` sit behind `AiEnabledGuard` plus `ai:use` (except `GET /api/ai/config`). Admin routes under `/api/admin/ai/*` require `ai_config:read`/`ai_config:write` and are deliberately **not** behind `AiEnabledGuard`.
5. **New AI settings cards follow the Settings UI Pattern and declare `feature: 'ai'`**, except the admin `AI` card.
6. **ShellKeep: terminal output reaches a model only after redaction and only when the server profile allows it** (#56). No raw scrollback, command output, SSH secret, host or user name leaves the API process toward a provider unredacted; a profile whose AI-output switch is off sends none. Suggested commands are inserted into the terminal, never run, without an explicit user action.

Guardrails: conformance suites `ai-kill-switch`, `ai-rbac-matrix`, `ai-secret-egress`, `ai-key-policy`, `ai-jobs-server-only`, `ai-no-sdk-leak`, `ai-orchestration-boundary`; an opt-out needs a written reason.

## MANDATORY: Invariants that are easy to break

Each is or will be enforced by tests.

- **SSH host keys are verified before any command runs** (#60). Trust on first use, store the fingerprint, refuse a changed key. No connection path (terminal, test connection, runbook, probe) may skip verification or auto-accept a changed key.
- **SSH secrets never leave the API process**: no log, span, metric label, export, API response, AI prompt, job payload or node. Stored in the platform credential store (`UserCredentialsService`, purpose `ssh`, since #48); only the decrypted value inside the SSH call.
- **The WebSocket gateway authorizes every connection and message**: validate the access token on connect, re-check ownership of the session or profile, never trust a client-supplied id.
- **`apps/api/prisma/schema/` is generated (applies from #45); never hand-edit it.** Edit the fragment (`apps/api/prisma/fragments/`, or the platform package's), run `npm run db:compose`, then `prisma:generate`.
- **An installed migration is never edited or renamed** (applies from #45). `prisma/platform.lock` records each sha256 and `npm run db:check` fails on any byte change, comments included. Until #45, never rewrite a migration that was applied anywhere.
- **Raw-SQL partial unique indexes are intentional schema drift.** Never "fix" one with `@@unique` or a `findFirst` pre-check; list it in `raw-sql-indexes.json`.
- **Row-level security is transaction-local and the API is never a superuser** (applies from #45, #52). `app.org_id`, `app.user_id`, `app.rls_bypass` are written only with `set_config(name, value, true)` as the first statement of a transaction (`forOrg`/`runInOrg`, `asSystem`); never a session-level `SET`. Never use a `forOrg` client inside `$transaction`. Only files in the `ALLOWLIST` of `apps/api/test/tenancy/system-injection-boundary.spec.ts` *(target)* may inject `PrismaSystemService`. A link between two org-owned tables is a composite FK including `org_id`.
- **Every dump and restore carries BOTH `--enable-row-security` and `PGOPTIONS=-c app.rls_bypass=on`** (the option in the environment, never argv). A backup archive is never buffered: `pg_dump` streams into object storage. No restore pre-flight creates, drops or renames anything.
- **`notify()` runs after the triggering write commits**, outside any `$transaction`.
- **A job `type` string is permanent** once jobs of that type exist; a rename is a new type.
- **The same-origin contract**: UI at `/`, API at `/api`, WebSocket at `/api/terminal/ws`, reference at `/api/docs`. Nginx routes them; do not add a second origin.
- **The mobile terminal affordances survive every UI change**: `TerminalView`, `TerminalKeyShortcutsBar`, `TerminalScrollButtons`, `useTouchScroll`, `useKeyboardInset` (details in `apps/web/AGENTS.md`).

## Architecture principles

1. **Separation of concerns**: the UI presents; the API handles all business logic and authorization.
2. **Same-origin hosting**: UI at `/`, API at `/api`, API reference at `/api/docs`.
3. **Security by default**: every endpoint requires authentication unless deliberately public. There is no global JWT guard in the target layout, so a route without `@Auth()` is public.
4. **API-first**: all business logic lives in the API layer.

## Security guidelines

- Deployment secrets come from environment variables (`infra/compose/.env.example`), never from code. Runtime-configured features (storage, AI, Web Push, SMTP) get no environment variable once their slice is adopted (#48, #50, #51, #55); do not add one. Email and Web Push are runtime-configured since #51.
- The access JWT (15 minutes) is read only from `Authorization: Bearer`; the only cookie is the HttpOnly `refresh_token`, rotated on use.
- Validate input on every endpoint (Zod from #41; class-validator until then) and every WebSocket message. Uploads: images only, size and type limits.
- The email allowlist restricts access; `INITIAL_ADMIN_EMAIL` bypasses it.
- Never log terminal content, credentials or tokens.

## Environment variables

- [`infra/compose/.env.example`](infra/compose/.env.example) is the reference; do not duplicate it. It is generated: platform variables in the package, app variables in `infra/compose/app.env.example`, then `npm run platform:infra:sync`. A platform variable that ShellKeep serves differently (`APP_URL`, `GOOGLE_CALLBACK_URL`, `APP_BIND_PORT`) is set in `.env`, not repeated in `app.env.example`.
- `DATABASE_URL` is built at runtime from `POSTGRES_*`: use `npm run prisma:*`, never bare `npx prisma`.
- **Never add a commented `# KEY=value` line** to `.env.example`; tooling reads it as a declared variable. Describe values as prose.

## Subagents

Delegate development work to the matching agent in `.opencode/agents/` (OpenCode) or `.claude/agents/` (Claude Code): `backend-dev`, `frontend-dev`, `database-dev`, `testing-dev`, `docs-dev`, `ops-dev` (container rebuilds, migrations, typecheck).
